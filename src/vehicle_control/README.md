# vehicle_control

`vehicle_control` is the only application package that depends on `px4_msgs`. Its PX4 adapter owns DDS topic names, command routing and acknowledgments, telemetry conversion, and ENU/NED conversion. The MAVSDK mission connection owns MAVLink upload and progress for onboard routes. The node publishes `VehicleState` and serves the internal `vehicle_control/takeoff`, `vehicle_control/navigate_to`, `vehicle_control/follow_trajectory`, `vehicle_control/orbit_point`, `vehicle_control/land`, and `vehicle_control/fly_mission` actions. `mission_execution` is their sole application client. External callers use the [mission-execution interface](../mission_execution/README.md). Vehicle control validates and executes the selected operation; mission execution owns intent admission, serialization, and landing preemption.

The adapter matches command acknowledgements by command and destination system/component. PX4 v1.17 does not set `VehicleCommandAck.from_external` when it publishes acknowledgements. Transition logs identify the stage, command, attempt, acknowledgement, and observed state change. Action errors include PX4 result codes and result parameters for non-accepted acknowledgements.

Compiled missions use fixed geographic destinations. Local telemetry and Offboard position setpoints use `local_enu` in meters from PX4's local-position origin. PX4 v1.17 local position and trajectory setpoints use NED, so the adapter maps ENU `(east, north, up)` to PX4 `(north, east, down)`.

`NavigateTo` leaves yaw unspecified when `look_at_target` is false. When enabled, it updates yaw at a maximum setpoint rate of 2 radians per second toward the horizontal bearing from the current position to the absolute `look_at_position` in `local_enu`. Position targets remain in ENU and do not rotate with yaw. Navigation succeeds after position is within its requested tolerance and yaw error is at most 0.2 radians for 0.5 seconds. PX4 controls the resulting attitude and rotor outputs.

`FollowTrajectory` controls position alone by default. Set `control_yaw` to true to interpolate each point's `yaw_rad`; the action then requires valid yaw telemetry and checks the final wrapped yaw error against `yaw_tolerance_rad` for 0.5 seconds. A zero tolerance selects the configured default. When `control_yaw` is false, yaw fields are ignored, `yaw_tolerance_rad` must be zero, and yaw error feedback and results are NaN. Yaw control ends when the action completes or cancels.

Flight actions are rejected while `enable_flight_commands` is false. The launch default is false. Enable it only after checking the vehicle, operator control link, PX4 preflight state, configured topic prefix, and system ID. Takeoff streams position setpoints for one second, enters Offboard when needed, confirms Offboard, and then arms. A takeoff request can reuse an already active Offboard mode. Navigation cancellation captures a current-position hold, retains the Offboard stream, and confirms position within the configured default tolerance and speed at most 0.3 m/s for 0.5 seconds before reporting canceled. Hold confirmation has a 12-second deadline; failure returns aborted. An externally selected mode is not overridden. Landing uses PX4's `VEHICLE_CMD_NAV_LAND`, waits for its land detector, disarms if needed, and selects Auto Loiter. The action succeeds after PX4 reports landed, disarmed, and in Auto Loiter. Position setpoints stop after touchdown and disarming. A later takeoff request starts the one-second prestream and can enter Offboard again.

`OrbitPoint` sends one PX4 `VEHICLE_CMD_DO_ORBIT` command. It accepts an armed, airborne rotary-wing vehicle in Offboard or native Hold with fresh global-reference and velocity telemetry. A Hold start establishes and settles Offboard before requesting Orbit. Its center is an absolute point in `local_enu`; the center altitude is the requested orbit altitude. PX4 performs the approach and circle. The action measures signed angular travel from position telemetry after the vehicle reaches the requested radius and altitude band. It rejects a missing or changed local reference, unsupported vehicle state, invalid radius or speed, and speeds above the 2 m/s² lateral-acceleration bound. Defaults limit the radius to 20 m, speed to 3 m/s, and center distance from the local origin to 100 m. These bounds are ROS parameters `max_orbit_radius_m`, `max_orbit_speed_mps`, and `max_orbit_center_distance_m`.

`OrbitPoint` leaves yaw uncontrolled by default. Set `face_center` to true to request PX4 center-facing yaw. The action then requires valid yaw telemetry, checks the wrapped heading error while the vehicle is on the orbit circle, and fails after two seconds outside `yaw_tolerance_rad`. It completes only while yaw is within tolerance. Zero tolerance selects 0.524 radians. A nonzero yaw tolerance requires `face_center`.

After completion or cancellation, `OrbitPoint` captures the current position, streams Offboard setpoints for one second, requests Offboard, and waits for position and velocity to settle. It reports success or cancellation only after Offboard hold is confirmed. If PX4 changes to another mode first or hold recovery fails, the action reports failure and leaves the active PX4 mode in control. A lost `DO_ORBIT` acknowledgment is not retried; the action checks `VehicleStatus.nav_state` before deciding whether Orbit began.

Vehicle lifecycle, goal rejection, and PX4 transition events use ROS logging. Rejection logs include goal values, telemetry freshness, and yaw validity. Failed action results include measured progress, PX4 state, and applicable tolerances. The control setpoint timer does not emit per-setpoint log messages.

The PX4 topic prefix is the full path through `fmu` and is independent of the ROS namespace. For example, application namespace `/uav_1` with PX4 prefix `/uav_1/fmu` resolves app actions under `/uav_1` and PX4 topics under `/uav_1/fmu/in/...` and `/uav_1/fmu/out/...`.

## Geographic planning telemetry

`VehicleState` publishes the validity-gated latitude, longitude, and AMSL altitude of the local ENU origin. `local_frame_revision` changes when PX4's reference timestamp, reference values, global-reference validity flags, or XY/Z reset counters change. Position samples without a frame change retain the same revision. `VehicleState.global_position_valid` gates the current geographic estimate, derived from fresh local position and a valid geographic reference. Compiled mission destinations do not use the estimator origin; PX4-specific telemetry remains inside this package. Geographic destinations and distance feedback remain fixed across local revisions. Local navigation aborts into current-position hold on a frame reset. An orbit tail projects its geographic center at handoff and checks subsequent reference changes.

## Uploaded missions

The internal `vehicle_control/fly_mission` action accepts fixed WGS84/AMSL takeoff and waypoint positions and a captured geographic starting position. Vehicle control validates coordinate ranges, start movement, and meter-based envelopes before encoding geographic destinations directly into mission items. MAVSDK 4.2.0 uploads raw takeoff, waypoint, optional ROI, and optional land items before arming. PX4 Mission mode executes the route without an Offboard stream.

`mission_connection_url` defaults to `udpin://0.0.0.0:14540`. The selected MAVLink autopilot must match `px4_system_id`. Configure a separate MAVLink endpoint for each vehicle. DDS remains required for status, position, command acknowledgments, and cancellation confirmation. `VehicleState.holding` and `VehicleState.mission` expose fresh native mode status.

Only one mission uploader may control a vehicle during an application run. Do not upload or select mission items through QGroundControl while a ROS mission is active. Cancellation confirms native Hold, or landed/disarmed state before takeoff. Telemetry loss and external mode changes return failure; active PX4 failsafes are not overridden. After successful uploaded landing, the terminal contract is landed and disarmed; Auto Loiter is not required.

Native Hold requires global position and follows PX4's configured Hold altitude policy. Standalone navigation, trajectories, and orbit accept native Hold and establish Offboard with a confirmed prestream and settled hold before their motion begins. Their cancellation behavior remains Offboard hold.

See the [onboard mission guide](../../docs/architecture/PX4-ONBOARD-MISSIONS.md) for native waypoint acceptance, retained code, operating constraints, and validation evidence.

`NavigateTo` accepts internal `wgs84` or `local_enu` goals. Public relative commands resolve in mission execution. Geographic navigation projects at this package boundary and is limited to 1,000 horizontal meters and 120 meters of height change from the current position. See the [coordinate guide](../../docs/architecture/COORDINATES.md).

Land detection freshness uses at least 2 seconds to cover PX4's once-per-second unchanged-state publication. Position and status freshness retain the configured `telemetry_timeout_sec`, default 1 second. A stale land detector still prevents touchdown confirmation.
